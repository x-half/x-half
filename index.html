01
什么是 AI Agent

AI Agent（智能体）是一个能够感知环境、做出决策、执行动作、并根据反馈持续调整的自主系统。与传统的单次 LLM 调用不同，Agent 具备跨多步骤的持久目标追踪能力，可以自主分解任务、调用工具、管理状态，并与外部世界交互。

🎯
目标导向
持有长期目标，自主规划达成路径
🔧
工具使用
调用外部 API、数据库、代码执行等
🔄
循环推理
感知→思考→行动→观察的反复迭代
💾
状态管理
跨会话维持上下文与工作进度

Agent vs. 单次推理的本质区别

维度 单次 LLM 调用 AI Agent
执行步骤一次输入→输出多轮迭代，动态步骤数
外部交互无（纯文本生成）调用工具、API、数据库
状态无状态有工作记忆、历史轨迹
自主性被动响应主动规划、决策、纠错
错误处理无法自我修正可观察错误并重试
核心公式： Agent = LLM（大脑）+ Memory（记忆）+ Tools（手脚）+ Orchestration（调度）
02
核心框架与架构模式

ReAct 框架（Reason + Act）

目前最主流的 Agent 范式，交替进行"思考"与"行动"，每个动作后观察结果并决定下一步。

// ReAct 循环伪代码
while not goal_achieved:
    thought  = LLM("Thought: 下一步该做什么？", context)
    action   = LLM("Action: 调用哪个工具？参数是什么？")
    obs      = execute_tool(action)
    context += [thought, action, obs]   # 追加观察到上下文

Plan-and-Execute 框架

先由 Planner LLM 生成完整计划，再由 Executor LLM 逐步执行。计划与执行分离，适合复杂长任务。

🧠
Planner
生成子任务列表
📋
Task Queue
有序任务队列
⚙️
Executor
逐步执行每项
🔍
Re-planner
失败时重规划
✅
完成
输出最终结果

Reflexion 框架

在 ReAct 基础上引入"自我反思"机制：任务失败后，Agent 对自身轨迹进行批评，将经验写入长期记忆，下次遇到类似任务时参考历史教训。

主流开源框架对比

框架 核心定位 架构模式 适用场景
LangChain 链式调用 + 工具集成 链/Agent/RAG 通用应用快速开发
LangGraph 有状态图执行 DAG/循环图 复杂多步工作流
AutoGen 多 Agent 对话 对话式协作 代码生成、辩论推理
CrewAI 角色化团队 分层 + 角色 业务流程自动化
OpenAI Agents SDK 原生函数调用 单/多 Agent GPT 生态集成

Agent 能力维度

感知能力（Perception）

Agent 接受的输入模态正在快速扩展：

文本 / 代码
Prompt、文档、源码、JSON/CSV
图像 / 视频
截图识别、图表解析、视频理解
结构化数据
数据库查询结果、API 响应
工具返回值
函数输出、Shell 结果、错误栈

记忆系统（Memory）

📥 In-Context Memory
当前 Prompt 窗口内的信息，最直接但受 Token 限制（4K~200K）
📚 External Memory
向量数据库（Pinecone/Chroma/Weaviate），存储语义化 Embedding，支持检索增强（RAG）
🗃️ Episodic Memory
历史对话记录、执行轨迹，用于 Reflexion 学习
🧠 Semantic Memory
知识图谱、实体关系，结构化世界知识
⚙️ Procedural Memory
微调后的模型权重，隐式编码的能力与偏好

行动能力（Action）

工具调用（Function Calling / Tool Use）

现代 LLM 原生支持结构化工具调用，输出 JSON Schema 描述的函数名 + 参数：

// OpenAI 工具调用示例
{
  "tools": [{
    "type": "function",
    "function": {
      "name": "search_web",
      "description": "搜索网页获取最新信息",
      "parameters": {
        "type": "object",
        "properties": {
          "query": { "type": "string" },
          "max_results": { "type": "integer", "default": 5 }
        }
      }
    }
  }]
}

常见工具类型分类

类别示例工具说明
🔍 信息获取web_search, RAG retrieval, SQL query获取外部知识
💻 代码执行Python REPL, Shell, Jupyter运行代码、数学计算
📁 文件操作read_file, write_file, list_dir读写本地/云端文件
🌐 API 集成HTTP call, OAuth, Webhook连接第三方服务
🖥️ 计算机控制click, type, screenshot, browserGUI 自动化（CUA）
👥 Agent 调用spawn_agent, handoff调用子 Agent
设计原则：工具描述的质量直接影响 Agent 的调用准确率。应包含：功能说明、参数含义、使用场景、输出格式、副作用提示（如"此操作不可逆"）。
04
执行链路详解

完整执行流程

用户输入 User Query → 预处理（意图识别、安全过滤）
上下文构建 System Prompt + Memory Retrieval + Tool Schemas
推理决策 LLM Inference → Thought + Action / Final Answer
工具执行 Tool Dispatcher → Tool Result (Observation)
循环/终止 Loop Controller → 继续迭代 or 返回最终结果

Token 流详解：一次完整的 ReAct 轮次

## System Prompt（角色 + 工具说明）
你是一个研究助手，可以使用以下工具：
- search_web(query): 搜索网页
- python_repl(code): 执行Python代码

## User Message
分析2024年全球AI芯片市场规模，并画出前三名厂商份额饼图

## Assistant Turn 1（思考 + 行动）
Thought: 需要先获取市场数据，再用Python绘图
Action: search_web
Action Input: {"query": "2024全球AI芯片市场份额排名"}

## Tool Result（工具返回）
Observation: NVIDIA 80%, AMD 8%, Intel 5%...

## Assistant Turn 2（继续推理）
Thought: 数据已获取，现在用matplotlib绘图
Action: python_repl
Action Input: {"code": "import matplotlib..."}

## Tool Result
Observation: [图像已生成，路径：/tmp/chart.png]

## Assistant Final
Final Answer: 以下是2024年AI芯片市场分析...

终止条件设计

Loop Controller 决策树
条件触发动作
LLM 输出 Final Answer: 标记✅ 正常终止，返回结果
达到最大步骤数（如 max_steps=15）⚠️ 强制终止，返回当前最优答案
工具调用连续失败 N 次❌ 错误终止，上报异常
检测到循环模式（同一动作重复）🔁 打破循环，注入提示
Token 预算耗尽💰 成本终止，返回部分结果

并行工具调用（Parallel Tool Calls）

现代框架支持在单个推理步骤中批量发起多个工具调用，显著减少串行等待时间：

// 并行调用示例（OpenAI API）
[
  { "id": "call_1", "function": { "name": "search_web", "arguments": {"query": "A"} } },
  { "id": "call_2", "function": { "name": "search_web", "arguments": {"query": "B"} } },
  { "id": "call_3", "function": { "name": "read_file", "arguments": {"path": "/data.csv"} } }
]
// 三个工具并行执行，延迟 = max(t1,t2,t3) 而非 t1+t2+t3
05
约束与安全护栏

Agent 的自主性越强，安全风险越大。约束系统是 Agent 工程中最不可忽视的组件，涵盖多个层级。

约束层级模型

L1 模型层
RLHF/Constitutional AI 训练的内置价值观，拒绝有害输出的能力
L2 Prompt 层
System Prompt 中明确的行为规则，如"不得删除用户数据"、"操作前必须确认"
L3 工具权限层
工具白名单/黑名单，只暴露允许的 API，最小权限原则
L4 输出过滤层
Guardrails 模型对 Agent 输出实时检测，PII 检测、有害内容过滤
L5 人工审批层
Human-in-the-loop，高风险操作（如删除、支付）需人工确认
L6 可观测层
全链路日志记录、异常告警、执行轨迹审计

常见风险与对策

风险类型描述防御措施
提示注入 工具返回值中包含恶意指令，操控 Agent 行为 工具输出隔离、输入沙箱、输出解析严格化
权限越界 Agent 访问了不应访问的资源 最小权限原则、OAuth scope 限制
无限循环 Agent 陷入死循环，持续消耗资源 最大步骤数、重复检测、超时熔断
幻觉操作 对不存在的工具或参数发起调用 工具调用格式校验、Schema 严格检查
费用失控 Token/API 调用超出预期成本 Token 预算、成本告警、每轮限速

Guardrails 设计模式

# 输入/输出双向守护（伪代码）
class AgentGuardrails:
    def validate_input(self, user_message):
        # 1. PII 检测（电话/邮件/身份证）
        # 2. 有害意图分类
        # 3. 越权请求识别
        return safe_message

    def validate_tool_call(self, tool_name, args):
        # 1. 工具白名单检查
        # 2. 危险参数检测（../路径穿越、DROP TABLE 等）
        # 3. 操作幂等性评估
        return approved

    def validate_output(self, response):
        # 1. 不应泄露的内部信息过滤

原则：不可逆操作必须人工确认。删除、支付、发送邮件等副作用操作，设计上应默认 Human-in-the-loop，而非默认自动执行。

上下文工程（Context Engineering）

上下文工程是 Agent 工程中最核心的技术领域——决定在每次 LLM 调用时，窗口里放什么、怎么放、放多少，直接决定 Agent 的推理质量与稳定性。

上下文的组成结构

┌─────────────────────────────────────────┐
│           LLM Context Window             │
├──────────────┬──────────────────────────┤
│ System Prompt│ 角色/能力/规则/工具说明  │
├──────────────┼──────────────────────────┤
│  Retrieved   │ RAG 检索结果 / 相关文档  │
│  Knowledge   │ 知识库 / Few-shot 示例   │
├──────────────┼──────────────────────────┤
│  Trajectory  │ 历史 Thought/Action/Obs  │
├──────────────┼──────────────────────────┤
│  User Input  │ 当前用户消息             │
└──────────────┴──────────────────────────┘

System Prompt 工程

System Prompt 是 Agent 的"宪法"，需要涵盖以下模块：

System Prompt 标准结构
  1. 角色与身份：明确 Agent 是谁、专长是什么
  2. 任务范围：能做什么、明确不能做什么
  3. 工具说明：每个工具的用途、参数、使用时机
  4. 输出格式：响应的结构要求（如 JSON、Markdown）
  5. 推理规范：Thought 格式、Chain-of-Thought 要求
  6. 边界规则：不确定时如何处理，错误时如何上报
  7. 示例（Few-shot）：高质量的输入→输出样例

上下文压缩策略

当执行轨迹过长时，需要对历史上下文进行压缩，以节省 Token 并保持关键信息：

策略方法适用场景
摘要压缩 用 LLM 对早期轨迹生成摘要 长会话、多轮任务
滑动窗口 只保留最近 N 轮，丢弃早期 任务有明确局部性
重要性过滤 保留包含关键事实的步骤 高密度信息任务
向量外置 将历史存入向量 DB，按需检索 超长会话、跨会话记忆

上下文工程最佳实践

信息密度优先
每个 Token 都应有意义，删除冗余的客套话和重复说明
关键信息置顶/置底
LLM 对首尾 Token 注意力更强，将规则和目标放在两端
结构化标记
用 XML/Markdown 分隔不同部分，帮助模型区分角色
动态注入
按任务阶段动态调整工具列表和 Few-shot 示例
Lost in the Middle 问题：研究表明 LLM 对上下文中间部分的信息召回率显著低于首尾。关键的工具描述、规则和约束应放在 System Prompt 开头或用户消息末尾，而非埋在中间大段文本中。

多 Agent 协作架构

协作模式

主从模式（Orchestrator-Worker）
Orchestrator 拆解任务，多个 Worker Agent 并行执行，结果汇总
辩论模式（Debate）
多个 Agent 对同一问题给出不同视角，互相批评并迭代收敛
流水线模式（Pipeline）
专业化 Agent 按序传递上下文，每个负责独立的处理阶段
群体模式（Swarm）
多 Agent 共享全局状态，动态 handoff，无中心协调

Agent 间通信协议

// Agent Handoff 消息格式（Swarm 风格）

    "constraints": {...},   // 传递约束条件
    "history_summary": "..." // 压缩的历史摘要
  }
}

多 Agent 挑战

挑战具体问题解决方案
状态一致性 多 Agent 修改共享资源产生冲突 乐观锁、事件溯源、共享黑板架构
错误传播 上游 Agent 错误被下游放大 每个 Agent 独立校验输入，设置检查点
成本叠加 N 个 Agent 的 Token 成本线性叠加 小模型 Worker + 大模型 Orchestrator 组合
死锁 Agent A 等 B，B 等 A 超时机制、依赖图检测

评估与优化

Agent 评估维度

任务成功率
最终输出是否满足用户目标，端到端的正确率
工具调用准确率
选择的工具和参数是否正确，调用成功率
步骤效率
达成目标所用的平均步骤数（越少越好）
Token 消耗
每次任务的输入+输出 Token 总量，成本指标
延迟
首 Token 时间（TTFT）和总完成时间
安全性
越权操作率、有害输出比例、注入攻击抵抗率

评估框架（LLM-as-Judge）

// 用 LLM 评估 Agent 执行轨迹质量
const judge_prompt = `
你是 Agent 行为评估专家，请对以下执行轨迹打分（0-10）：

任务目标: {task}
执行轨迹: {trajectory}

评估维度：
1. 推理逻辑性（Thought 步骤是否合理）
2. 工具选择准确性
3. 错误处理能力
4. 最终答案质量

以 JSON 格式输出每个维度的分数和理由。
`

常见优化手段

Prompt 优化
优化 System Prompt、工具描述、Few-shot 示例，是 ROI 最高的手段
轨迹微调
收集高质量 Thought-Action 轨迹对模型微调，提升工具调用准确率
工具精简
减少无关工具数量，降低 LLM 选择混淆的概率
模型分层
简单决策用小模型（如 Haiku），复杂推理用大模型（如 Opus）
黄金法则：先在小规模测试集上建立评估基准，再迭代优化。没有评估指标的 Agent 优化等同于在黑暗中摸索。
